# Справочник правил DDD

Пути от `manager/`. Это требуемая форма. Если код ей противоречит, верен этот файл. Зачем деление: [объяснение](ddd-explanation.md). Как добавить код: [инструкция](ddd-howto.md). Расчёт склада, чертежа и производства: [домен станции](station-domain.md).

## Слои

Бизнес-логика описывает процессы, состояния и инварианты станции.

Инфраструктура: ORM-модели, SQL, HTTP DTO, контроллеры и обработчики, внедрение зависимостей, брокер сообщений, менеджер транзакций, логирование, кэш, клиенты внешних API.

| Слой | Путь | Что лежит |
| --- | --- | --- |
| Бизнес | `internal/station` | агрегат, entity, value object, команды, интерфейс репозитория |
| Сценарии | `internal/services` | сервисы |
| Инфраструктура | `internal/http`, `tools`, `cmd` | HTTP, SQL, сборка зависимостей |

Бизнес-код не импортирует инфраструктуру. Обработчик вызывает сервис. Сервис вызывает агрегат через интерфейс репозитория. Реализацию репозитория передаёт `cmd`.

## Агрегат

Основная единица бизнес-логики и транзакционная граница. Агрегат станции — `Station` в `internal/station/entities`.

- Снаружи агрегат меняется только методом корня. `station.Storage` и вызов метода вложенной части из сервиса запрещены. Нужен метод корня: `station.ApplyPurchase(...)`.
- Поля — entity или value object. Примитив допустим только если за полем нет бизнес-правила.
- Поля открыты. Сервис может их читать. Писать в поля может только репозиторий, когда собирает объект из базы. В остальных местах присваивание поля запрещено. Это договорённость: компилятор её не проверяет.
- Агрегат небольшой.
- Другой агрегат хранится ссылкой по ID, не вложенным объектом.
- Есть поле `version`. По нему видно, синхронизирована ли локальная копия с базой.

## Entity

Объект со своим ID. Держит часть логики агрегата. В `Station` это склад, хранилище чертежей и модуль производства. Состояние entity меняет метод корня, не сервис.

## Value object

Примеры вида: деньги, адрес, email, период, телефон. В станции это идентификаторы, деньги (`Cost`), эффективность материала, чертёж.

- Неизменяемый: после создания поля не меняются.
- Сравнивается по значению, не по ссылке.
- Всегда проверяет себя сам. Вызывающий это правило не копирует.
- Может содержать несколько полей. Чертёж — такой объект.
- Один и тот же тип могут держать несколько entity.

Деньги не бывают `float` и не бывают примитивом.

## Репозиторий

К агрегату прилагается интерфейс. Для станции он лежит рядом с `Station`:

```go
type StationRepository interface {
    Save(station Station) (values.StationID, error)
    Take(id values.StationID) (Station, error)
}
```

- `Save` возвращает ID агрегата. Этого ID в базе нет: insert. ID есть: update всех entity, которые принадлежат агрегату.
- `Take` возвращает агрегат целиком, со всеми entity, не часть станции.
- При `Save` репозиторий сравнивает `version` с базой. Версии совпали: запись проходит, `version` становится новой. Не совпали: ошибка, строка в базе не меняется.

Реализация в `tools` содержит SQL и ORM и не содержит инвариантов станции.

## Сервис

`StationService` в `internal/services`. Это бизнес-код: пакет `tools` он не импортирует.

- Принимает команду из `internal/station/commands`. Отдельный DTO сервиса командой не является.
- Описывает сценарий, который не помещается в один агрегат.
- Читает и пишет базу только через репозиторий.

Один агрегат, та же форма: `Take`, метод корня, `Save`. Доменная ошибка: вернуть её, `Save` не вызывать.

Несколько агрегатов: `Take` каждого, метод каждого корня, `Save` каждого изменённого внутри одной транзакции инфраструктуры. Менеджер транзакций в сервисе не реализуется.

## Команда

Команда — вход сценария. В ней нет обращения к базе и нет инварианта агрегата. Сервис передаёт её в метод корня.

## Цепочка вызова

HTTP, затем команда, затем сервис, затем `Take`, затем метод корня, затем `Save`, затем результат, затем HTTP.

Обработчик не вызывает агрегат и не пишет SQL. Агрегат не импортирует HTTP и `tools`.

Чтение без изменения: `Take`, метод просмотра корня, без `Save`.
